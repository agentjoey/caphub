this machine (Docker is not installed here); the Dockerfiles are verified indirectly — `npm ci` and
`npm run build` succeed from the committed lockfile, and `npx tsx scripts/worker.ts --dry-run` with no
env vars exits non-zero with a Zod config-validation error (not a crash stack) — and the actual image
build is verified at the first Railway deploy.

## Migrations

Migrations run **locally only**, using the Neon owner connection string, never from Railway:

```bash
npm run migrate
```

This applies schema migrations (e.g. `001` creating `caphub_v2`) against the Neon `caphub` project's
main branch. After the schema exists, grant the app role access (run once, as owner):

```sql
CREATE ROLE caphub_v2_app LOGIN PASSWORD '<generated by Neon, not committed>';
GRANT USAGE ON SCHEMA caphub_v2 TO caphub_v2_app;
GRANT SELECT, INSERT, UPDATE, DELETE ON ALL TABLES IN SCHEMA caphub_v2 TO caphub_v2_app;
GRANT USAGE, SELECT ON ALL SEQUENCES IN SCHEMA caphub_v2 TO caphub_v2_app;
GRANT USAGE ON SCHEMA caphub TO caphub_v2_app;                -- read-only access for v1 import
GRANT SELECT ON ALL TABLES IN SCHEMA caphub TO caphub_v2_app;
```

Railway's `DATABASE_URL` is then set to the `caphub_v2_app` connection string via the dashboard (or
Railway MCP `set-variables`, with the Human supplying the password out-of-band).

## Rollback

Roll back a bad deploy by redeploying the previous successful deployment for the affected service in
the Railway dashboard ("Redeploy" on the prior deployment), rather than reverting git history. Both
`web` and `worker` are redeployed independently since they build from different Dockerfiles.

## Cost settings

- Both `web` and `worker`: replicas = 1.
- `web`: Railway app sleeping enabled where the plan supports it (idles when there is no traffic).
- `worker`: sleeping disabled — it must keep running to poll the run queue and sweep retention.
